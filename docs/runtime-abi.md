# Core Protocol Runtime ABI

本文定义 Core Protocol 当前接受的 executable runtime 目标。历史 `js-esm` packaging 已实现，但在 v0.1.0 前由 #31 收敛为明确的 Cordis Plugin ABI；spec 与实现应在 docs 稳定后再投影。

## ABI v1

```text
runtime.kind = "cordis-js-esm"
runtime.abi = 1
```

ABI v1 每个 Protocol 只有一个 gzip-compressed ESM executable artifact。该 artifact 是已经完成构建的、可由 Host 直接加载并挂载的 Cordis Plugin bundle，不是源码包、npm package 或需要节点再次安装/编译的工程目录。

链上 identity 承诺最终 executable bytes：

```text
source
-> build / bundle
-> single Cordis Plugin ESM
-> gzip
-> exact artifact bytes
-> ArtifactHash
-> ProtocolHash
```

因此 build 属于 Protocol 发布侧；Repo Node / runtime 不得根据源码重新 bundle、transpile、install 或重新生成另一份 executable artifact。

## Required module export

`cordis-js-esm` ABI v1 使用一个明确的 named export：

```ts
export const plugin = {
  name: 'core.record@0.1.0',
  inject: [],
  apply(ctx) {
    // register this Protocol implementation's capability
  },
}
```

导入后的 ESM namespace MUST 只暴露 `plugin` 这一项 runtime export。`plugin` MUST 是可直接传给 `ctx.plugin()` 的 Cordis object Plugin，并至少具有可调用的 `apply(ctx, ...)`。`name` 用于诊断；`inject` 使用 Cordis 自身的 dependency contract。

Protocol capability 不通过任意 ESM exports 暴露。实现需要提供给其他 Protocol 的能力时，应在 `plugin.apply()` 中通过 Cordis Service / `ctx.provide()` 等 Cordis 原生机制注册，使其生命周期归当前 Fiber 管理。

Core 的纯函数 package API（例如 `recordId()`、`verifySignature()`、`recordsRoot()`）仍可作为源码/包级 API 存在；它们由 thin runtime wrapper 使用，不直接成为 Protocol artifact 的任意 module exports。

ABI 不重新定义 Cordis Plugin、Context、Fiber、Service、inject、effect 或 lifecycle。

## Host loading boundary

给定已经解析到的 exact artifact bytes，Host / Repo Node 负责：

```text
resolve exact gzip artifact bytes
-> verify ArtifactHash / ProtocolHash
-> bounded gunzip
-> materialize/import ESM
-> require exact `plugin` export shape
-> verify semantic dependency projection
-> ctx.plugin(plugin, config?)
-> Cordis Fiber / inject / lifecycle
```

这里的 gunzip、缓存、临时文件/materialization、ESM import 和 mount 都属于加载过程，不属于重新构建 Protocol。

Host MUST NOT：

```text
compile TypeScript
transpile source
run a package install
resolve npm dependency ranges for the Protocol
execute install scripts
rebundle the Protocol
replace the verified artifact with locally generated bytes
```

这样同一个 ProtocolHash 在不同节点上对应同一份 executable bytes，而不是“同一源码在不同节点各自构建出来的某个结果”。

ABI v1 将解压后的单个 runtime bundle 限制为最多 **1 MiB**。超过该规模的 executable 应优先拆分为更多 Protocol，或把非执行内容移到 Asset / Runtime。

## Cordis runtime ownership

Protocol artifact 包含 Protocol implementation，不携带一份私有 Cordis runtime。Cordis 由 Host 提供并作为唯一 runtime/composition system。

Protocol 源码可以使用 Cordis type-only imports 来获得开发期类型；构建后的 artifact 不应为了实现 Plugin contract 而 bundle 第二份 Cordis runtime。

因此：

```text
Host Cordis
-> import verified Protocol artifact
-> obtain artifact.plugin
-> ctx.plugin(artifact.plugin)
```

而不是：

```text
Host Cordis
-> Protocol artifact containing another Cordis runtime
-> second plugin/lifecycle system
```

## Protocol dependencies and Cordis inject

`Protocol.dependencies[]` 与 Cordis `inject` 是同一依赖关系在两个层面的表达，但权威性不同：

```text
Protocol.dependencies[]
= chain-facing semantic dependency
= exact name + version + ProtocolHash
= participates in ProtocolHash

plugin.inject
= runtime service dependency
= controls when Cordis may activate the Fiber
```

每一个 chain-level `ProtocolDependency` MUST 投影为一个 required Cordis service dependency：

```text
protocol:<name>@<version>
```

例如：

```text
Protocol.dependencies[]
- name: core.entity
  version: 0.1.0
  protocolHash: <exact hash>

plugin.inject
- protocol:core.entity@0.1.0
```

Host 仍必须按 `protocolHash` 解析和验证 exact dependency implementation；`inject` 本身不替代 ProtocolHash authority。

`plugin.inject` MAY 额外声明 runtime-only Cordis services，例如 storage/logger 等。这些 runtime capability dependencies 不进入 `Protocol.dependencies[]`，也不进入 ProtocolHash。

因此：

```text
project(Protocol.dependencies[]) ⊆ plugin.inject
```

而不是要求两者完全相等。

Protocol implementation 对外提供自身 capability 时使用 canonical service key：

```text
protocol:<name>@<version>
```

由于 service key 不包含自身 ProtocolHash，不会形成 artifact bytes -> ProtocolHash -> artifact bytes 的自引用。Host 在挂载前负责确认当前 service key 对应的 descriptor identity 与 exact ProtocolHash；同一 isolation scope 内相同 `name@version` 不应同时映射到两个不同 ProtocolHash。

## Artifact identity

实际发布、可选上链和下载的是 gzip bytes 本身：

```text
ArtifactHash = DoubleSHA256(exact gzip artifact bytes)
```

`artifactHash` 进入 ProtocolHash。可选 `Protocol.artifact` 只是 exact gzip bytes 的 canonical Base64 链内承载，不进入 ProtocolHash。

因此“artifact 是否 embedded on-chain”与“artifact 是否 ready-to-mount”是两个不同问题：

- embedded / external 决定 bytes 从哪里取得；
- `cordis-js-esm` ABI 决定取得的 bytes 已经是最终可执行 Plugin bundle。

无论 bytes 来自 Genesis Record、本地 cache、GitHub Release、mirror 或其他 resolver，Node 都验证并加载同一 exact artifact，不重新构建。

## Build / Node responsibility split

Protocol Dev SDK #23 负责发布侧工作：

```text
source entry
-> bundle ordinary source/build dependencies
-> construct thin Cordis Plugin wrapper
-> enforce explicit `plugin` export
-> deterministic gzip
-> ArtifactHash / ProtocolHash
-> diagnostics / release preparation
```

Repo Node / runtime 负责消费侧工作：

```text
resolve
-> verify
-> bounded gunzip
-> import
-> validate plugin export/dependency projection
-> mount in Host Cordis
-> cache / dispose / reload through runtime lifecycle
```

这个边界允许链只保存 descriptor + optional exact artifact bytes，而不要求每个节点携带 Protocol build toolchain。

## Current Core migration

当前四个 Core Protocol 的实现代码仍以纯 API ESM bundle 生成 artifact。#31 后续 spec/implementation 应为它们增加 thin Cordis Plugin runtime entry，并把 runtime kind 从历史 `js-esm` 迁移为 `cordis-js-esm`。

迁移会改变 artifact bytes、ArtifactHash 与 ProtocolHash；由于 v0.1.0 尚未发布，这属于预发布 identity 收敛，不需要保留旧 `js-esm` compatibility path。

Genesis #10 消费最终冻结后的 ordinary Protocol values / ProtocolHashes；本 ABI 不定义 Genesis-specific Record 或 Block 规则。
